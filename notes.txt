3. ServiceNow Integration Workflow — bi-directional sync + duplicate prevention + queue hygiene
“Bi-directional sync would work like this: when OpsIQ’s correlator groups anomalies into an incident, a Lambda calls ServiceNow’s Incident API to create the record, tagging it with a correlation ID we generate. From that point, the sync runs both ways — status changes made by an engineer in ServiceNow (acknowledged, resolved, closed) get pulled back into OpsIQ via polling or ServiceNow’s outbound webhook, so our dashboard reflects the real state instead of going stale.
For duplicate ticketing specifically: before creating a new ServiceNow incident, OpsIQ checks two things — (1) does an open incident already exist with this correlation ID (meaning we already ticketed it), and (2) does the new anomaly’s topology/CI overlap with an existing open incident’s affected CIs within a rolling time window. If either is true, we append the new anomaly to the existing incident as related evidence rather than opening a second ticket. This is the same principle as CI-based alert aggregation — group by affected component, not by raw alert text.
For queue hygiene: incidents that get all their underlying anomalies clear (metrics return to baseline) get auto-flagged for closure review rather than sitting open, and we’d suppress re-notification on an already-open incident so the same root cause doesn’t keep re-alerting the queue. That auto-close/suppress logic isn’t built yet in the POC — the create-and-correlate path is — but it’s a defined next step, not an unknown.”
4. Knowledge Activation (GenAI) — specifically surfacing runbooks from ServiceNow’s Knowledge Base
“The mechanism I’d use is retrieval, not generation from memory: when OpsIQ creates an incident, before calling Bedrock, a Lambda queries ServiceNow’s Knowledge Management API for KB articles tagged against the same CI or service that’s affected — matching on the CMDB relationship, not just keyword search on the incident text. Those matched articles get passed into the Bedrock prompt as grounding context, so the model’s summary references and links actual existing runbooks rather than inventing remediation steps.
That’s a retrieval-augmented generation (RAG) pattern: search ServiceNow KB by CI/service → pass matched articles as context → Bedrock synthesizes an incident summary that cites which runbook applies and why. It also solves the trust problem — the SRE sees where the recommendation came from, not just an AI-generated paragraph. Today OpsIQ’s Bedrock call only has the structured incident record as context, no KB retrieval yet — that KB lookup step is the concrete next build, not a re-architecture.”
