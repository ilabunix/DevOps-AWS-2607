I dug further into the TaskTop DEV instance and reviewed both the server.xml and the TaskTop properties template to understand how the instance-level certificate is supposed to be installed.

TaskTop is listening on HTTPS/8443 and the active Tomcat connector is configured to load the certificate from a Java keystore using:

server.ssl.key-store
server.ssl.key-store-password
server.ssl.key-store-type
server.ssl.key-alias

The TaskTop properties file specifically shows the expected keystore type as JKS, with an absolute path to the keystore file on Linux.

So for UAT, the clean approach would be to first decide the TaskTop UAT FQDN/DNS name, request the Venafi cert for that hostname, import the cert/private key/chain into a JKS keystore, place the JKS on the EC2 instance, and then point the server.ssl.* properties to it.

We could automate that as part of the deployment as well — for example, store the JKS securely in encrypted S3, keep the keystore password in Secrets Manager, and have the EC2 instance role pull them during bootstrap/deployment.

I would avoid using the EC2 private IP as the certificate CN. The CN/SAN should be the stable FQDN they decide to use for the TaskTop UAT instance.
