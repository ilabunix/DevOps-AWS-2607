IMPORTANT COMPASS LOGGING CONTEXT

Compass application processing logs are stored in an ECS CloudWatch log group.

For DataLite, EASy Inbound, WPO Inbound, and similar Compass processing jobs, the relevant application-processing events are normally written to the ECS data-processing log stream matching:

/adt-frfs-compass-${env}-e-tg-dp

When constructing CloudWatch Logs Insights queries, prefer restricting the query to this processing log stream whenever technically appropriate so that unrelated logs from other ECS streams do not contaminate the results.

Do not assume every new playbook uses identical messages, though.

The PLAYBOOK and actual log examples are the source of truth.

PHASE 4 — DESIGN CLOUDWATCH LOGS INSIGHTS QUERIES

Construct queries based on the actual new job.

Reuse the STYLE of proven DataLite queries where appropriate, but DO NOT copy DataLite-specific log patterns unless the new playbook uses them.

Queries should:

* target the appropriate Compass ECS log group
* constrain the data-processing log stream when applicable
* distinguish this specific job from other Compass jobs
* avoid counting unrelated integrations
* support Grafana time ranges
* tolerate normal log variations
* avoid brittle exact-string matching when a safer structured pattern exists
* extract useful fields where possible
* aggregate correctly for the panel type

Where useful, parse fields such as:

* filename
* job name
* status
* correlation ID
* batch ID
* record count
* error message
* exception type
* processing duration

Do not invent log fields.

If a required field is not shown in the playbook/log examples, explicitly flag it.

⸻

QUERY VALIDATION

For every query ask:

1. Could this accidentally match another Compass job?
2. Could retries cause duplicate counts?
3. Could one logical job generate multiple matching messages?
4. Does the query represent jobs, records, files, or log lines?
5. Does “completed” truly mean successful completion?
6. Could expected business exceptions be counted as failures?
7. What happens when no jobs run during the selected time window?
8. What happens if the application produces no logs at all?
9. Is the stream restriction correct?
10. Is aggregation appropriate for Grafana?

Prefer operational correctness over visually impressive metrics.

For count/stat panels where zero is a healthy or valid result, configure the panel so that lack of matching log events displays something appropriate such as:

Do not globally convert every no-data situation into zero.

PHASE 7 — APPLICATION ALERT DESIGN

ALERT CATEGORIES

Consider alerts such as:

Job Failure

Trigger when a job reaches a confirmed failed state.

Missing Expected Job

If a scheduled job is expected but no successful execution occurs within its operational window.

Only create this when schedule expectations are clear enough to implement safely.

Processing Exception

Only for exceptions requiring intervention.

Download / File Acquisition Failure

When required inbound files cannot be obtained.

Validation Failure

When validation prevents processing and requires investigation.

Downstream Integration Failure

When Compass cannot deliver/process data with a dependent service.

Repeated Failure

When retries repeatedly fail and operational intervention is required.

Long Running / Stuck Job

Only when the playbook gives enough information to establish a meaningful threshold.

Do not manufacture thresholds.

Critical:
