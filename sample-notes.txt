## 2. What OpsIQ actually does today (POC capabilities)
- **Ingestion:** Kinesis-based streaming pipeline ingesting operational signals from simulated product accounts.
- **Anomaly detection:** Bloom filter–based pipeline flags anomalies efficiently at scale before they hit the correlation stage.
- **Correlation:** SQS-fed correlator groups related anomalies into a single incident instead of raw alert noise — same underlying goal as ServiceNow Event Management and AWS DevOps Guru.
- **Storage & real-time delivery:** DynamoDB backs incident state; WebSocket pushes updates live to a React 18 dashboard on CloudFront/S3.
- **AI summarization:** Amazon Bedrock (Claude Haiku, cross-region inference profile) generates incident summaries on-demand — only invoked when a user clicks "Generate AI Summary" or uses the chat panel, keeping cost controlled.
- **Design language:** Deliberately styled to match AWS Console conventions (navy top bar, orange primary, table-first layouts) — feels native to AWS operators, not a generic dashboard.
- **Deployment maturity:** Fully built and actively deploying in a commercial AWS sandbox — 12+ CloudFormation stacks covering ingestion, storage, IAM, Lambda, API Gateway, WebSocket, DynamoDB, dashboard. This is real infrastructure, not mockups.

## 3. How OpsIQ compares to what's already on the market

ServiceNow is strongest on CMDB/correlation, AWS is strongest on native cloud detection, OpsIQ is the only one of the three you've personally proven end-to-end and can speak to from real build experience.

## 4c. If Person A asks ME directly (my own POV, not a critique of AWS)

Person A is likely asking these four questions of AWS *and* of me — he wants my thinking on event correlation, not just my assessment of vendors. These are my own answers, grounded in what OpsIQ actually does.

**1. Inbound Data Ingestion & Normalization**
> "My approach: normalize everything into a single event schema at the point of entry, regardless of source. In OpsIQ, every signal gets pushed onto a Kinesis stream in a common format. Deduplication and noise filtering happen early, using a Bloom filter, before anything reaches correlation. That means correlation and AI never have to know or care whether an alert came from CloudWatch or Dynatrace — the hard part is the adapter at the edge, not the pipeline behind it. Most of our tools (Grafana, Prometheus, Dynatrace, ServiceNow) support outbound webhooks, so the ingestion pattern is largely repeatable across sources."

**2. Contextual Correlation & Root Cause**
> "Correlation without topology is just clustering by time and text similarity — useful, but shallow. Real root-cause isolation needs two things layered together: topology (what's connected to what, from the CMDB) and change awareness (what changed recently near the affected service). Right now OpsIQ's correlator groups events without CMDB context; the next real step is having it query ServiceNow's CMDB and Change tables so grouping is topology-aware, not just pattern-based. I'd rather be upfront that this is unbuilt today than overclaim it."

**3. ServiceNow Integration Workflow**
> "Bi-directional sync is non-negotiable for adoption — if the correlation engine can't write back into ServiceNow Incident and read from CMDB/Change, ops teams end up maintaining two systems of truth, which defeats the purpose. Architecturally this is a straightforward REST integration on our end: ServiceNow's Table API for CMDB reads, and a Lambda writing incidents back via ServiceNow's Incident API when OpsIQ creates one. I see this as the highest-leverage integration to build next."

**4. Knowledge Activation (GenAI)**
> "This is the one I have real hands-on lessons on. The mistake to avoid is letting the LLM freelance a root cause — it needs to be grounded in the actual correlated incident data, not just raw alert text. In OpsIQ, Bedrock only generates a summary on-demand from the structured incident record, not a raw prompt, which keeps hallucination down and keeps cost controlled. Extending that to surface real runbooks from ServiceNow's Knowledge Base means giving the model retrieval access to KB articles — a RAG pattern, not a bigger prompt."

## 5. What's genuinely feasible to add to OpsIQ next (future evolution)
- **ServiceNow CMDB pull:** scheduled Lambda via ServiceNow Table API, cached in DynamoDB, referenced by the correlator for topology-aware grouping. This is real architecture work (changes how correlation logic works), not just a new adapter.
- **ServiceNow Incident push (bi-directional sync):** Lambda calling ServiceNow's REST API on incident creation/update — directly answers Person A's bullet 3.
- **Prometheus / Amazon Managed Prometheus:** remote_write query or Alertmanager webhook → API Gateway → Kinesis. Low effort, same pipeline.
- **Grafana:** ingest FROM Grafana Alerting via webhook contact points → API Gateway → Kinesis. (Note: Grafana *querying* Redshift is a Grafana-side capability already, separate from OpsIQ's pipeline.)
- **Dynatrace:** Problem Notification webhooks → same adapter pattern.
- **CloudWatch / Trusted Advisor / AWS Health:** already the easiest — native EventBridge rules straight into Kinesis, no custom adapter needed.
- **Cross-account production rollout:** the planned "product-account-agent" unit extends the same pattern from simulated accounts to real cross-account production signals.

**Core architectural strength to emphasize:** every new source becomes (webhook/pull) → normalize into existing event schema → same Kinesis entry point → same Bloom filter/correlator/DynamoDB/WebSocket pipeline. The correlation and Bedrock summarization logic doesn't need to change per source — that's the strongest evidence the design is genuinely extensible, not a one-off demo.
